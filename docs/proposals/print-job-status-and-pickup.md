# 提案：打印任务状态、异常解释与取件记录

## 动机 / 用户故事

用户发送打印后需要知道进度、异常原因和完成后的取件结果，而不是去设备或厂商应用中猜测任务状态。

## 目标用户

- 已提交打印任务的普通用户
- 处理异常和取件的设备管理员

## 本期范围

本期做：显示统一 `PrintJob` 状态、进度、预计剩余时间、打印机和耗材；将设备错误转为用户可理解说明；完成后创建 `PickupRecord` 并记录取件。

本期明确不做：复杂调度、多机自动分配、远程控制面板、摄像头失败检测、自动重打、取件柜、短信核销和社区反馈。

## 关键决策与依据

用户只看到平台统一状态 `queued / printing / paused / failed / completed / picked_up`，而非厂商原始状态；异常必须同时包含解释、建议和原始错误码；仅完成后生成取件记录。

## 基本概念与信息结构

- `PrintJob`：状态、进度、时间、耗材、最后错误和更新时间
- `PrintException`：错误码、原始信息、展示标题、解释、下一步和严重度
- `PickupRecord`：取件码、状态、取件时间和操作人

## 验收标准

### 例子 1：打印中查看进度

- 现状：用户离开页面后无法获知执行情况。
- 提议后的行为：任务页显示 `printing`、进度、预计剩余时间、设备和耗材。
- 验收：每项值来自同一 `PrintJob`，页面可观察到状态更新。

### 例子 2：可解释异常

- 现状：设备术语不能指导新手处理。
- 提议后的行为：`FILAMENT_LOW` 显示“耗材不足”和建议下一步。
- 验收：暂停或失败页保留原始码，同时展示解释和建议。

### 例子 3：完成与取件边界

- 现状：打印完成与实际取件混为一谈。
- 提议后的行为：完成时创建待取件记录，确认取件后才变为 `picked_up`。
- 验收：未完成状态不能生成可用取件码；取件后记录时间与操作人。
